# Action Sequences Module


## Overview

The Action Requests module is responsible for processing abstracted action
requests in the game. It provides a structured way to define 'action requests'
and handle queuing them for execution by the game engine. The game uses action
requests to represent high-level actions derived from raw player input. For
example, a right click can be mapped to several action requests like a
'UIRightMouse', 'ActionCancel', 'UISkipDialog', and 'ContextMenu'. The game
then determines which action request to execute based on the current context.


## How user input is handled
User input is first captured by `SDL_PollEvent` by a function I call
`rawInputHandler` as discussed in the 'Move Internal Cursor' module. The game
then creates a struct I call `UnifiedInputEvent` for each SDL input event
(sometimes more than one for a single SDL event like for mouse movement). These
`UnifiedInputEvent`s are then pushed into some queue for async processing.

Another function I call `processUnifiedInputQueue` then processes the pending
events (the same function we hook in `src/Hooks/process_input_hook.cpp`). This
function then calls another function I call `processUnifiedInputEvent` for each
`UnifiedInputEvent`. This function is responsible for mapping the input event
to a player index first in the case of (I assume) split-screen multiplayer. It
then maps the input to all the game bindings it is associated with. Key 'esc',
for example, could be mapped to game pause, action cancel, and UI close. For
each binding it finds, it then creates an `ActionRequest` struct and pushes it
into the corresponding queue. At the end, it calls a function I call 
`processActionRequestQueue` to process the pending action requests. This
function _seems_ to pick the _winning_ action request. I am not 100% if that's
correct, but the reason for my suspicion is that if we push multiple action
requests like 'CameraRight' and 'CameraForarwd', only one of works (the one we
sent first). This means that after we push the set of action requests, we have
to trigger the processing of the action request queue. So, we need to make sure
that any set of action requests pushed at once also correspond to a single
final action we want to perform based on the game context.


## Motivation
For many touch input gestures, we can't just translate them directly to some
mouse or keyboard input. We need a higher level of abstraction to represent the
specific action we want to perform for that gesture and prevent any undesired
interference from other input bindings. We also don't have to enforce specific
keybinding settings on the user.

These 'actions' have string names that we can search for in the game's binary.
This makes them very easy to find and use. Since we figured out the
`ActionRequest` struct, we are able to hook the `pushToActionRequestQueue`
function and find out all the action requests that get triggered for any input
with all the values we need.

Also, they let us follow the game's intended flow more easily, so we aren't
changing structs like some global UI or global camera struct. We get to 
basically start the 'input' flow almost from the beginning and take advantage
of all the game logic associated with those actions without having to worry
about side-effects.


## Solution
We will analyze the `ActionRequest`s generated by the game for a particular
input that performs the action we're interested in. We can then replicate
the action requests (or a subset of them) and push them directly to the action
request queue. The next time `processUnifiedInputEvent` runs, it will process
the queue with our action requests and figure out the correct action to
perform.

However, some gestures like a two-finger swipe creates two action requests that
both need to be processed: the X camera pan and the Y camera pan. So, for we
will instead manually call `processUnifiedInputEvent` as well with a dummy F24
key up event after pushing our action requests. We could call the function
`processActionRequestQueue` directly, but `processUnifiedInputEvent` might be
doing some extra work with side effects that I don't fully understand from the
disassembly. So, to be safe, we will just call the higher-level function.
